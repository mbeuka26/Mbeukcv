MbeukCV

Déploiement de A à Z

Un push sur la branche main déclenche GitHub Actions. Le workflow vérifie la sécurité, dépose les clés, publie les Edge Functions sur Supabase, puis publie le site sur Vercel. S’il manque une clé ou s’il trouve une faille dans le dépôt, il s’arrête et l’erreur reste dans le journal GitHub.

Avant toute commande

Ce guide ne contient aucune clé. Ne collez jamais une clé dans ce fichier, dans un message, ni dans le code. Vous les saisissez une fois dans GitHub. Le workflow les recopie ensuite.

Le fichier actif est .github/workflows/deploy.yml à la racine du dépôt. Cette racine est le dossier qui contient mbeukcv-saas et mbeukcv-pro-v2. Le nom du produit est MbeukCV. Le site principal est le SaaS. Le bouton « MbeukCV Pro » ouvre /pro/index.html, construit pendant le workflow.

Les migrations SQL ne partent pas toutes seules. Les lancer automatiquement sur la base de production pourrait casser les données. Elles restent une étape manuelle, plus bas.

Ce que le workflow fait

Supabase, puis Vercel

Après un push sur main, et seulement si le job « Contrôles de sécurité » est vert, le job « Supabase puis Vercel » fait ceci, dans cet ordre :

  1. Il vérifie que les secrets GitHub obligatoires sont présents. Il n’écrit pas leurs valeurs dans le journal.
  2. Il dépose les secrets Edge du SaaS sur Supabase avec supabase secrets set.
  3. Il déploie les Edge Functions du SaaS, copiées depuis mbeukcv-saas/supabase/edge-functions, avec supabase functions deploy.
  4. Si SUPABASE_PRO_PROJECT_REF est renseigné, il dépose les secrets de MbeukCV Pro sur l’autre projet Supabase et déploie les fonctions de mbeukcv-pro-v2/supabase/functions. Sans cette référence, Pro reste utilisable en local et cette étape est sautée. Le déploiement SaaS ne s’arrête pas pour autant.
  5. Il construit MbeukCV Pro avec VITE_BASE=/pro/ et le place dans le site, au chemin /pro/index.html.
  6. Il dépose les variables de production sur le projet Vercel, puis il publie le site avec vercel deploy --prebuilt --prod.

Les fonctions publiées sont : hub-auth-login, hub-auth-logout, hub-auth-refresh, hub-auth-register, hub-auth-forgot-password, hub-checkout, hub-diagnostics, hub-license-status, hub-me, hub-sync-license, hub-validate-promo, validate-trial.

Une pull request lance seulement les contrôles. Elle ne touche ni Supabase ni Vercel. Vous ne retapez pas les clés dans les écrans Vercel ou Supabase : si vous les changez, vous les changez dans GitHub, puis vous poussez à nouveau.

Ce workflow ne déploie pas MbeukCV Pro (mbeukcv-pro-v2), ni ses fonctions generate-docs, collect-offers, source-keys. Il ne pose pas COLLECT_KEYS_KEY. Pro reste une publication séparée.

Commandes à taper, dans l’ordre

PowerShell. Le déploiement en ligne, lui, est le dernier git push. Vous ne lancez pas vercel ni supabase functions deploy à la main.

cd "C:\Users\NATEIVA DOUALA\MBEUKSAAS\mbeukcv"
cd mbeukcv-saas
npm run security
npm test
cd ..
git status
git add .
git commit -m "Préparer le déploiement de MbeukCV."
git push -u origin main

Ensuite, ouvrez l’onglet Actions du dépôt. Si l’environnement production a un reviewer, approuvez le job « Supabase puis Vercel ». Un journal vert veut dire : secrets Edge déposés, fonctions déployées, variables Vercel déposées, site publié.

Étape A

Contrôle local

Dans PowerShell, depuis le dossier du projet :

cd "C:\Users\NATEIVA DOUALA\MBEUKSAAS\mbeukcv\mbeukcv-saas"
npm run security
npm test

La dernière ligne attendue du contrôle est OK — barrière de sécurité locale passée. S’il affiche BLOQUÉ, corrigez cette ligne avant de pousser. Le fichier .env.local peut exister sur votre machine : il est ignoré par Git.

Étape B

Générer les secrets qui vous appartiennent

Lancez la commande une fois par secret. Ne réutilisez pas la même valeur pour deux secrets. Gardez chaque résultat dans un gestionnaire de mots de passe, pas dans le dépôt.

[Convert]::ToBase64String((1..48 | ForEach-Object { Get-Random -Maximum 256 }))

À générer ainsi : ENCRYPTION_KEY (32 caractères minimum), CRON_SECRET (16 minimum), MBEUK_AUTH_BRIDGE_SECRET (32 minimum), CREDIT_GRANT_SECRET si vous activez le crédit automatique.

Étape C

Créer le dépôt GitHub

cd "C:\Users\NATEIVA DOUALA\MBEUKSAAS\mbeukcv"
git init
git add .
git status

git status ne doit pas lister .env, .env.local ni .env.production. S’ils apparaissent, ne les ajoutez pas.

git commit -m "Préparer le déploiement sécurisé de MbeukCV."
gh repo create mbeukcv-saas --private --source=. --remote=origin

Sans GitHub CLI, créez un dépôt privé vide sur github.com, puis :

git remote add origin https://github.com/VOTRE_COMPTE/mbeukcv-saas.git
git branch -M main
git push -u origin main

Étape D

Créer les projets Vercel et Supabase

Sur Vercel, créez un projet vide relié plus tard à ce dépôt, ou notez les identifiants d’un projet déjà créé. Il vous faut l’identifiant d’équipe (VERCEL_ORG_ID) et l’identifiant de projet (VERCEL_PROJECT_ID). Le jeton se crée dans Vercel, Account, Tokens. Donnez-lui uniquement ce projet.

Sur Supabase, le jeton d’accès se crée dans Account, Access Tokens. La référence du projet est l’identifiant dans l’adresse https://REFERENCE.supabase.co. C’est SUPABASE_PROJECT_REF.

Le produit et l’application se créent dans le portail développeur du Hub. Leurs identifiants sont des UUID : MBEUK_PRODUCT_ID et MBEUK_APPLICATION_ID. Sans ces deux UUID, le workflow s’arrête. C’est voulu.

Étape F

Protéger l’environnement production

GitHub, Settings, Environments, New environment, nom exact : production. Ajoutez Required reviewers avec votre compte. Le workflow ne publie qu’après votre approbation. Une pull request lance les contrôles, elle ne publie pas.

Étape G

Pousser et lire le résultat

git push -u origin main

Ouvrez l’onglet Actions du dépôt. Le job « Contrôles de sécurité » passe en premier. Ensuite « Supabase puis Vercel » attend votre approbation si vous avez activé les reviewers.

Ce que le contrôle vérifie, sans afficher les valeurs :

  • aucune clé serveur dans les écrans du navigateur ;
  • aucun NEXT_PUBLIC_ pour la clé Hub, le rôle service, RapidAPI, Claude, Brevo ou le cron ;
  • la clé service reste dans un module server-only ;
  • le cron refuse la collecte si CRON_SECRET est absent ;
  • l’activation de crédit compare le secret sans fuite de durée ;
  • les tables métier ont le verrouillage par ligne dans supabase/schema.sql ;
  • les en-têtes empêchent l’affichage du site dans une autre page ;
  • une alerte haute ou critique nouvelle dans les dépendances bloque. Les alertes Next.js 14 déjà connues, dont le correctif npm exige Next.js 16, sont signalées et ne bloquent pas.

Étape H

Si le journal affiche BLOQUÉ

Le déploiement s’arrête à la première série en échec. Ouvrez le job rouge, cherchez la ligne BLOQUÉ —. Elle nomme la règle ou le secret, pas sa valeur.

Exemples : secret absent : MBEUK_PRODUCT_ID, format UUID attendu, clé serveur visible côté client. Corrigez, commitez, poussez à nouveau. Tant que le contrôle est rouge, Vercel et Supabase ne sont pas mis à jour.

Étape I

Migrations SQL, à la main

Dans l’éditeur SQL du projet Supabase métier, dans cet ordre, et seulement après les avoir relues :

  1. supabase/schema.sql si les tables métier ne sont pas encore là ;
  2. supabase/migrations/000_mbeukcv_hub_cache.sql ;
  3. 001_hub_integration.sql ;
  4. 002_hub_identity_clarification.sql ;
  5. 003_licenses_access_type_compat.sql ;
  6. 004_lockdown_entitlement_rls.sql.

Le workflow ne lance pas ces fichiers. Le verrouillage par ligne fait qu’un client connecté ne lit que ses lignes. Le rôle service reste sur le serveur.

Étape J

Vérifier après une publication verte

  1. L’adresse Vercel ouvre la page Compte.
  2. Créer un compte Hub sans licence ne crée pas encore l’espace, et propose l’achat.
  3. Dans Supabase, Edge Functions, les fonctions hub-auth-login et hub-auth-register sont présentes.
  4. Dans Supabase, Edge Function Secrets, les noms MBEUK_HUB_API_KEY et MBEUK_AUTH_BRIDGE_SECRET existent. N’ouvrez pas les valeurs dans un ticket.
  5. Une collecte d’offres sans le secret de cron répond 401.

Ce workflow n’attaque pas la base et ne remplace pas un audit humain. Il empêche de publier un dépôt qui expose une clé, qui oublie un secret obligatoire, ou qui retire les garde-fous déjà écrits.
